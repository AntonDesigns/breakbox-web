The idea

what BreakBox is, in one breath.

BreakBox is my own reverse engineering lab. It hands me a small program to crack, I take it apart, and each one teaches a single idea about how protections work and why they fail. On top of that I built my own tools to do the taking-apart, and a pipeline and containers so the whole thing runs like real software, not a school folder. It is offensive and defensive at once: I learn to break, and from breaking I learn to defend.

Right now it is stateless. No accounts, no stored data, nothing to steal, and I have not built past that yet. The next step I am researching is turning it into a real, secured data system on purpose, so I have a live target I built to attack and defend myself. Not to prove I can write a login, that part is standard, but to learn the whole break-and-defend cycle on a data system, the web-and-data half of what I already do on binaries.

The application today, part by part

every component that exists right now, and why it is shaped the way it is.

The launcher React

The shop window. It lists the levels and downloads them, and it is the only thing a person actually clicks. It talks to my API through a single file that holds the one URL, so if I ever lock the origin down or move it, I change it in one place.

security: it is a dumb client on purpose. It shows what the server allows and nothing more. It never holds an answer, because it cannot be trusted with one.

The API and the generator C# / Roslyn

The heart. For every download it compiles a brand new target in memory with the Roslyn compiler, so no two people get the same file. It works out the valid key on the server and puts it aside. Only the compiled program is sent back.

security: this is the never trust the client rule made real. The key exists only to check answers, server side. A download can never carry its own solution, because the solution is never in it.

Core, the contracts SOLID seam

A small project of interfaces and plain data types, and nothing else. The controller depends on IChallengeProvider, an idea, not on a concrete class. That one decision is why I could swap a fixed provider for the real generator by changing a single line, and nothing else moved.

why it matters: the same seam is how I will drop the database in later without rewriting the app. Depend on the idea, swap the thing behind it.

BreakBox Studio Avalonia desktop

My own toolkit, one real app I run. Peek opens a compiled assembly and reads its methods, its strings, and the method that looks like the check, using Mono.Cecil, the honest small version of a decompiler. Keygen recovers the Level 2 seed and walks the reverse step by step, letting me compute the serial myself before it reveals anything.

security: read only, always offline. It never runs a target and never touches the server. Pointing it at a file is safe, and it proves the lesson that compiled code hides almost nothing.

The levels the ladder

The path from easy to expert: a plain stored key, then a computed serial, then patching a real app, then obfuscation and anti-debugging, a native memory overflow, weak crypto, an integrity check, and safe malware analysis. Levels 1 and 2 are built and playable; the rest are the plan, one clear idea each, and a rung only opens once I have actually built it.

scope: only my own generated targets, only authorised use. I break what I make.

The pipeline and the containers CI/CD · Docker

Every push builds, runs the tests, and runs three security scans: leaked secrets, vulnerable dependencies, and vulnerable code. Docker packages the API and the launcher so the whole thing comes up with one command, the same on any machine, and a health endpoint says whether it is alive.

security: the scans are the boring breaches caught automatically. The same set I would bring to any serious project.

The decisions, and why

the choices I have researched and plan to make, worth signing my name to so I can defend them and change them on purpose.
Store MySQL 8 (InnoDB), behind EF Core and the repository interface, with SQLite for quick local runs. A real database to secure, and the swap costs nothing because nothing above the repository knows which one it is.
Passwords argon2id, salted, tuned cost. Never reversible, never plaintext, never logged. A stolen dump is not a stolen login.
Sessions a signed token with a short life, checked on every request. The token proves who you are; the authorization layer decides what that lets you touch.
Access every query is scoped to the owner in the repository, not in the controller. Putting it at the lowest layer means a new endpoint cannot forget it.
Secrets connection strings and keys in environment config and local user-secrets, never in the repo. My secret scan and .gitignore guard this, and the MySQL account is least-privilege so a leak is not the end.

The build order

the order I plan to build it in. Pixler and Flip are the cracking half of Sprint 2, the database the defending half. Each step should run and be tested before the next lands on it.
  1. Pixler and Flip: the patch-a-real-app level and my patcher tool, the offensive half.
  2. Schema and migrations: the core MySQL tables, versioned with EF Core migrations.
  3. Accounts: register and log in, argon2id hashing, the signed session.
  4. Authorization: scope every read and write to the owner, then try to break it myself.
  5. Hardening: least-privilege role, secrets out of code, encryption at rest, the audit log.
  6. Prove it: tests for the access rules, and the pipeline scans now covering the data code too.

What building this gives me

the reason any of it is worth the effort.

By the end I will have designed a data system, built it, attacked it, and hardened it, with my own hands and my own reasons. That is the difference between knowing you should hash a password and understanding, from having done it, why argon2id and not a fast hash, why the check belongs in the repository and not the controller, why the database account must not be able to drop a table. The pipeline that guards every push

security is not only in the running app. It runs on every push, before anything ships.

The security you can see in the app is half of it. The other half runs in the pipeline, before a single line reaches anywhere. Every push builds, runs the tests, and runs three security scans. If a scan finds something, the change does not go through. That is shift left: the boring breaches, a leaked secret, an old library with a known hole, a risky pattern in the code, get caught automatically instead of in production.

When is it “expert”? My definition, from the standards

I do not call things expert to sound impressive. Expert has a definition here, and it comes from the research, so I can prove it to a teacher.

OWASP's ASVS (Application Security Verification Standard) sets three levels: L1 opportunistic, L2 the standard for most apps, L3 advanced for high-value systems. So proficient means meeting the OWASP Top 10 baseline; expert means verifying against ASVS L2 heading to L3, plus the supply-chain standards (SBOM, SLSA) that reach beyond my own code. That is also the line between the HBO-i levels: level 3 meets the standard, level 4 adopts the emerging standards and can advise on them, and that is where I aim. When I write EXPERT, this is exactly what it means.

Proficient meet the OWASP Top 10; CI builds and tests. The standard, met. HBO-i level 3.
Advanced verify against OWASP ASVS Level 2, and add SAST, dependency and secret scanning to the pipeline.
Expert verify against ASVS Level 3 (per-control, defence in depth); secure the supply chain with an SBOM and SLSA build provenance; track maturity with OWASP SAMM. Beyond my own code, and able to advise on it. HBO-i level 4, where I aim.

Expert, domain by domain (with the standard that says so)

baseline, then what I build, then the research that makes it expert, not my opinion. This is how I justify each EXPERT tag.

Passwords & login

Baseline: “hash the password” (Top 10 A02, Cryptographic Failures).

Expert: argon2id, memory-hard with a tuned cost, and a constant-time verify so a wrong guess costs the same time.

Says so: OWASP Password Storage Cheat Sheet (argon2id is the first choice) · ASVS V2.

Access control

Baseline: check the user is logged in on each endpoint (function-level).

Expert: object-level authorization — every row scoped to its owner in the repository, so IDOR is closed at the lowest layer.

Says so: OWASP A01 Broken Access Control · ASVS V4.

Injection & data access

Baseline: parameterise the queries.

Expert: parameterised queries and a least-privilege database role and input never run as code — two independent controls, so one failing is not the end.

Says so: SQL Injection Prevention Cheat Sheet · ASVS V5.

Data at rest & secrets

Baseline: do not commit secrets.

Expert: encryption at rest, automated secret scanning on every push (gitleaks), a least-privilege role, and a full audit trail.

Says so: Cryptographic Storage & Secrets Management Cheat Sheets.

The pipeline (supply chain)

Baseline: build and test. Advanced (mine now): SAST (CodeQL) + dependency + secret scanning + a SonarQube quality gate.

Expert (growing): an SBOM (a bill of every dependency), signed artifacts with build provenance, and a container image scan. Beyond my own code, into the supply chain.

Says so: SLSA (build provenance) · OWASP CI/CD Top 10 · OWASP SAMM.

Logging & monitoring

Baseline: log errors.

Expert: security-event logging (who did what, from where) plus detection rules over the audit data — the Level-9 board.

Says so: OWASP Logging Cheat Sheet · ASVS V7.

“But isn't it easy to break a system you built yourself?”

the honest objection, answered up front.

It is the first thing someone asks, so I answer it head on. Knowing the source does not make the defence weaker, it makes the attacker stronger. A full-knowledge attacker, me, holding the code, the schema and the keys, is the hardest case a system can face. If a control still holds when I know exactly how it works, then it never depended on the attacker being in the dark. That is the point: no security through obscurity.

So building both halves is not a shortcut, it is the test. I attack the database and the pipeline with every advantage I could have, and only the controls that survive that get to stay. The offensive levels get harder because the protection on the target gets real; the defensive half gets harder because I am the one trying to get through it. Proving to myself that it holds against me is worth more than hoping it holds against someone who knows less than I do.

The one rule

everything above collapses into a single sentence.

Never trust the client, and never depend on a secret that ships to it. That is the rule the whole plan is built around. Pixler is how I will test the offensive side once I build it: a licence check inside the program is a bit I can flip. The database is how I will test the defensive side: keep the check on the server, scope the data to its owner, never treat input as code. Same rule at both ends, and proving it to myself by building and attacking both is what I am actually after.

Use cases

not app plumbing like "browse a list" — the two things this project is actually for: attack, and defend.

BreakBox is a reverse-engineering lab first: I generate a target and crack it, and the target's protection climbs every level (read a key, then reverse an algorithm, then patch a real app, then beat obfuscation, then a native memory bug). That offensive ramp is the spine. Because I am also becoming a security engineer, the database and the pipeline are hardened to expert level, and I attack them myself before I defend them. So the real use cases are break and defend; the login/progress plumbing exists to make the lab run, but it is not the point.

UC5 · Harden the data layer (attack it first) EXPERT

UC6 · Gate every change through the pipeline EXPERT

Goal: a green build must also mean nothing insecure got in.

UC7 · Watch for attacks should-have

Defend S4 planned

Goal: see my own system being attacked, and learn to spot it.

Main flow: the monitoring view reads the audit_log and failed-attempt tables and flags brute force, IDOR probing and injection attempts. The defensive stretch, designed in the Roadmap.

The nine levels (the reverse-engineering ladder)

the real ladder, straight from my level catalog. Levels 1 and 2 are made and playable; the rest are defined and arrive in the sprints above. Level 9 is the hardest crack, Keysmith, not the monitoring.

Each level adds one idea, so I learn one thing at a time. This is the offensive spine of BreakBox; the secure-data use cases above are the defensive half I run alongside it.

Level 1 · Password

Easy S1 made

A plain key comparison. I find the check and read the key straight out of it. Tools: dnSpy.

Level 2 · Serial

Medium S1 made

The key is checked by an algorithm. I reverse it and write a keygen. Tools: dnSpy, my keygen.

Level 3 · Pixler

Hard S2 planned

A small photo app with a locked premium feature. I patch the licence check. Tools: dnSpy, Flip.

Level 4 · Protected

Expert S3 planned

Pixler again, with obfuscation and anti-debugging over the check. I get past the protection first. Tools: dnSpy, x64dbg, de4dot.

Level 5 · Overflow

Expert S3 planned

A small native C program with a planted bug. I crash it, exploit it, then defend it. Tools: Ghidra, x64dbg.

Level 6 · Cipher

Hard later planned

The key is hidden with weak crypto. I break it, then redo it properly. Tools: dnSpy, CyberChef.

Level 7 · Sentinel

Expert later planned

The program checks itself and refuses to run if patched. I defeat the integrity check, then build one. Tools: dnSpy, x64dbg.

Level 8 · Specimen

Expert later planned

I analyse a sample's behaviour safely in a VM and write detection for it. No malware is created. Tools: REMnux / FLARE VM, Ghidra, YARA.

Level 9 · Keysmith

Expert later planned

The key is made by a protected, obfuscated routine. I reverse the whole thing and build a keygen. The hard version of Level 1. Tools: dnSpy, x64dbg, my keygen.

Research, and the choices I made

for each decision: what I looked at, whether the reference fits my context, and why I chose what I chose.

My coach said security is a broad field, and my group said to explain our choices and to check whether a reference architecture actually fits our own context instead of copying it. So this is where I do that. Each card is one decision, in my own words, with the reasoning I can defend in a coaching meeting.

1 · The stack: React + ASP.NET Core (C#)

Looked at: my group already builds in C# and React; I could have used a lighter Python or Node stack for a lab.

Fits my context? Yes. The whole point is that what I learn flows straight into the group app, so a different toolchain would break that link.

My choice: React + ASP.NET Core, because I am already strong in it and everything I do here transfers to the project I ship.

2 · Three repos, not one

Looked at: one monorepo (how I started), or splitting BreakBox into three repos: frontend, backend, and my security tooling (Studio, keygens, scan configs).

Fits my context? As the security engineer, isolation is the lesson. Three repos give me separate access control, separate CI and security scanning, and least privilege per repo, so a problem in one does not reach the others. The backend already splits into small projects, but that is still one blast radius; three repos is three.

My choice: split into three repos (frontend, backend, security), because thinking in trust boundaries and blast radius is the security-engineer habit I want to build, even though a monorepo is simpler on a solo project. The group project stays its own separate repo.

3 · Generate a fresh target, not ship fixed files

Looked at: bundling pre-built crackmes (like crackmes.one) versus compiling a new target on each download with Roslyn.

Fits my context? A fixed file leaks the moment one person shares the answer; a per-request build stays unique.

My choice: Roslyn generation, so no two downloads are the same and the answer never ships inside the file.

4 · A SOLID seam (interface + DI)

Looked at: wiring the controller straight to the generator, versus depending on an interface.

Fits my context? I knew I would swap a fixed provider for the generator, and drop in a database later, without rewriting the app.

My choice: the controller depends on IChallengeProvider, an idea, not a class. Swapping the implementation was one line and nothing else moved.

5 · Mono.Cecil for Peek, not just a decompiler

Looked at: using dnSpy or ILSpy as-is, versus building a small inspector on Mono.Cecil.

Fits my context? I want to understand what a decompiler does underneath, not only click one.

My choice: Mono.Cecil for my own Peek, while I still crack with dnSpy. Building the small version is how I prove I understand it.

6 · The data store: MySQL + EF Core behind a repository

Looked at: the standard layered web-app reference (controllers → services → repositories → ORM → database). I checked whether it fits my context, not just copied it.

Fits my context? Yes. It gives me one seam to swap SQLite for MySQL, and one place (the repository) to enforce access control, which is exactly the thing I want to attack and defend.

My choice (built): MySQL 8 + EF Core behind a repository interface, now built as a DbContext + initial migration (SQLite for local, both behind the same seam); the ownership check at the lowest layer is Sprint 2, so a new endpoint cannot forget it.

7 · Passwords: argon2id, not a fast hash

Looked at: SHA-256, bcrypt and argon2id, against the OWASP password-storage guidance.

Fits my context? Yes. A fast hash is cheap to brute force; the reason I hash at all is that a stolen dump must not become stolen logins.

My choice (planned): argon2id with a tuned cost, plus a short-lived signed session, because it is the current recommendation and I can explain why not a fast hash.

8 · Attack visibility: make an attack something you can see

Looked at: how you even know you are being attacked — a structured audit log, rate-limit and lockout counters, and a small dashboard that surfaces failed logins, injection attempts, IDOR and integrity failures.

Fits my context? This is the payoff for the client: I can show a breach attempt being seen and stopped, instead of only claiming the app is secure.

My choice (researching now): a small attack dashboard fed by the audit log, so an attack shows up in real time. Still work in progress — I am deciding how far to build it.

9 · CI/CD and deployment

Looked at: the standard pipeline (build → test → scan → image) on GitHub Actions and Docker, and how complex to make deployment.

Fits my context? The build, test and scan part clearly fits. The deploy complexity does not decide itself — that depends on what the client actually needs.

My choice: GitHub Actions + Docker with build, test/validation and image stages now, and a deploy-dev step I will size after asking the client how complex they want the deployment.

10 · Future threads: B2B SaaS multi-tenancy & vector databases researched, not built

Looked at: where my security work points next. A B2B SaaS is multi-tenant (many businesses on one system), so its core rule, that tenant A never sees tenant B, is my row-scoping at company scale, and it is the shape of the Bosch camera platform I am security lead on. A vector database stores embeddings and finds nearest neighbours: useful for security as anomaly detection (flag outlier logins or events by distance) and sample similarity (a semantic cousin of YARA, for Level 8), and it brings new attacks to break: embedding inversion, RAG poisoning, and the same tenant-isolation problem inside the store.

Fits my context? The multi-tenancy maps straight onto what I built: scope every row to its owner, in one place, so a new endpoint cannot forget. Vector-DB security is current, HBO-i level-4 material and fits “build then break”. But a vector store does not belong in this relational reverse-engineering lab yet.

My choice (researched, NOT built): keep these as future threads. The multi-tenant framing justifies the data design now; the vector-DB piece I take on as an advanced defensive thread later in the sprints: a second, vector database showing how the current wave of company data leaks happens through shared AI stores, and how the same row-scoping stops it (drawn out in the Security tab). And I keep the tools straight: vector DBs for the AI's retrieval and memory, a graph DB for attack paths (the BloodHound shape), relational for the structured records. Knowing which store fits which job is the point. I have only read into this so far; it is not a conclusion, and nothing here is built.

The database schema

the tables and how they connect, in crow's foot notation. The shape, not the SQL.

This is the schema I am designing for the data system, not one I have built. One users table owns everything; every other table carries a user_id that points back to it, and that foreign key is the line the authorization layer would read to decide what belongs to whom. A user has many rows in each table, so every join is one to many.

Should S2-S3

Could S3-S4

Attack monitoring (the defensive Level-9 board), the Protected level (obfuscation + anti-debugging), the native Overflow target, and, as an advanced defensive thread, the AI data-leak showcase: a second, vector database that demonstrates how companies leak through shared AI stores and how the same row-scoping stops it. Stretch goals: I do them only if the core is solid, so scope stays honest.

Won't this semester

A real multi-user production deployment, creating actual malware (analysis and detection only, never creation), and fully polishing Levels 6-9. Out of scope on purpose, so I finish and can defend what I do build.

A should-have: attack monitoring

a defensive stretch for the end, not one of the nine levels. (Level 9 is Keysmith, a crack.)

The nine levels are reverse-engineering challenges. This is different: because I am the security engineer, I want a defensive should-have at the end, a view where I watch my own system being attacked and learn to spot it. It reads the security tables from the database, applies simple rules, and surfaces what looks wrong on a board I watch. It is a should-have, so it only happens if the core ladder is on track.

For the group: a detection architecture

the same idea, sized for the client app, as a proposal I would bring to the team.

A detection layer for the group project proposal

For BreakBox the monitoring is a should-have I build to learn. For the group app the same shape scales up: every service writes structured security logs to one central place; a small detection layer runs rules over them (failed-login bursts, access-denied spikes, unusual request shapes) and raises an alert instead of a dashboard I stare at.

Why this shape: it keeps detection out of each service (one place to reason about), and it starts simple, rules I can explain, rather than a heavy tool we cannot justify to the client. I would size how far to take it with the client, the same way we agreed to size the deployment.

Definition of done

what “done” means on this project, so I am not marking things finished by feel. Each grain has its own bar, and nothing is done until it clears it.

A level is done when

  • the generator serves a fresh, unique target for it;
  • I can beat it the intended way (read the key, write a keygen, or patch the check);
  • a test builds a target and verifies the crack;
  • the walkthrough is written.

A piece of code is done when

  • it sits behind an interface (the SOLID seam), so it can be swapped and tested;
  • it has a unit test;
  • CI is green: build, tests, the three security scans, and the SonarQube gate;
  • no secret is committed;
  • a real decision behind it is captured as an ADR.

A security control is done when

  • I can name the attack it stops;
  • it lives on the server, never only on the client;
  • it is verified against the ASVS level I claim for it;
  • I have attacked it myself and it held.

A sprint is done when

  • everything I mark built runs and has tests;
  • the design sheet and the docs say built versus planned honestly;
  • I have had coach or peer feedback;
  • the portfolio is updated.

The project is done when

  • Levels 1-2 are crackable and the data layer is secured and attacked by me;
  • there is a shareable build, a five-minute demo, and a reflection;
  • each of the five HBO-i outcomes is evidenced at the level I claim.
